# v3.23.7 — PDF da Proposta Georref: anexos não vazam, footer global, QR garante espaço

**Data:** 2026-05-21
**Origem:** CEO reportou que **PROP-2026-0013-R1** ainda saía com 3 bugs do PROP-12: (1) anexos do cliente concatenados no PDF da proposta (págs 6-11 com plantas, matrículas, fotos), (2) páginas 4 e 5 redundantes (hash repetido + linha solta com "Proposta válida 15 dias"), (3) suspeita de texto cortado nas seções 7 e 8. Investigação mostrou que **nenhum fix tinha sido escrito ainda** — o diagnóstico anterior pediu confirmação que ficou pendente. Esta release implementa os 3 fixes.

## Fix 1 — Anexos não vazam mais no PDF principal (CRÍTICO)

**Causa raiz:** `gerarPdfPropostaConsultoriaCompleto` (linha 1713) fazia merge da proposta com anexos via `pdf-lib` e era o **default** do endpoint `/pdf`. Cliente externo (cartório, MPF, INCRA) que abria o link público `/v/:hash/pdf` recebia um arquivo único de 10+ páginas misturando a proposta técnica com plantas/matrículas/fotos do imóvel.

**Fix:**
- Função renomeada: `gerarPdfPropostaConsultoriaCompleto` → `gerarPdfPropostaConsultoriaComAnexos`. Lógica do merge preservada — só roda quando explicitamente solicitada.
- Endpoint `GET /api/propostas-consultoria/:id/pdf` **INVERTEU o default**:
  - Antes: default = COMPLETO (com merge); `?somente_principal=1` para versão limpa
  - Agora: **default = só proposta principal**; `?incluir_anexos=1` opt-in para versão merged
  - Compat retro: `?somente_principal=1` continua aceito (no-op redundante hoje)
- Rota pública `GET /v/:hash/pdf`: usa só a proposta principal. Anexos seguem acessíveis via API autenticada `GET /api/propostas-consultoria/:id/anexos`
- `enviarPropostaConsultoriaWhatsApp`: envia proposta + cada anexo em mensagem separada com **throttle de 1.5s** (rate-limit Z-API). Retorna contagem `anexos_enviados / anexos_total`
- `enviarPropostaConsultoriaTelegram`: idem (Telegram aceita até 30 msgs/seg por chat, throttle leve)

**Mudança de comportamento documentada no PR description** — qualquer integração que dependia do merge default precisa adicionar `?incluir_anexos=1`.

## Fix 2 — Páginas redundantes 4 e 5 eliminadas

**Causa raiz:**
- QR + hash renderizados em coords absolutas `y=720` (hardcoded)
- Footer "Romatec — Proposta válida por X dias" em coord absoluta `y=800` (text() avulso)
- Se o conteúdo passava de y=720 antes de chegar no QR, PDFKit auto-criava nova página, o footer caía em página solta com 1 linha

**Fix:**
- `PDFDocument` agora criado com `bufferPages: true`
- QR/hash renderizam **relativo a `doc.y`** com guard: se `espacoRestante < ALTURA_QR_BLOCO (100px)` → `addPage()` antes
- Footer movido pro fim via loop `doc.bufferedPageRange()` — emite em **TODAS as páginas**:
  - Esquerda: `Romatec Consultoria Total — Açailândia/MA · Proposta {numero} · Emitida {data} · Validade {N} dia(s)`
  - Direita: `Página X de Y`
- Footer antigo `text(..., y=800)` removido

Resultado: nenhuma página solta no fim. Cada página tem rodapé consistente com numeração `X de Y`.

## Fix 3 — Texto cortado nas seções 7 e 8 (verificação)

**Investigação:** o helper `renderGeorrefRuralBody` (introduzido em v3.23.5) já renderiza as seções 7 (Documentos) e 8 (Avisos) em **1 coluna full-width** com `width: COL_W - 8 = 491px` (largura útil A4 menos margens). Não há layout de 2 colunas nesse helper.

**Hipótese:** o corte de texto reportado em PROP-2026-0013-R1 era provavelmente **efeito colateral do merge via `pdf-lib`** — `PDFLibDocument.load(propostaPdf)` + `copyPages` re-codifica o PDF original e pode comprometer fonte/largura. **Fix 1 elimina automaticamente esse caminho** (o `/pdf` e `/v/:hash/pdf` não passam mais por pdf-lib quando o cliente vai baixar/visualizar).

Testes garantem que o helper continua usando `COL_W - 8` (anti-regressão).

Validação empírica final fica pendente para inspeção visual em prod (PROP-2026-0014).
