```sql
ALTER TABLE tenant_users

  ADD INDEX idx_tu_role_equipe (role, equipe_id);
```

## Comportamento de fluxo

1. CEO acessa `/login` no celular
2. Digita email ou telefone + senha. Front faz POST `/api/auth/login`
3. Backend busca user em `users` (por email OU phone), verifica `password_hash` com bcrypt, busca `tenant_users` pra pegar role + equipe_id, emite JWT (8h colaborador / 24h admin), seta cookie `zayra_auth` httpOnly
4. Front redireciona conforme `user.role`:
   - `colaborador` → `/minha-quinzena` (implementação na PR B)
   - demais → `/obras` (painel admin atual)
5. Sessão segue via cookie httpOnly. `requireAuth` middleware lê o cookie em rotas protegidas (ou Authorization Bearer pra clients API)
6. Logout: front chama POST `/logout`, server blacklista o jti, limpa cookie

## Segurança

- ✅ Senhas em bcrypt cost 12 (~250ms hash time)
- ✅ JWT em cookie httpOnly + Secure (em prod) + SameSite=Strict — imune a XSS
- ✅ Rate limit 5 falhas/15min por IP em `/login`
- ✅ Log de toda tentativa (sucesso + falha) em `auth_logs` — SEM senha
- ✅ Increment `failed_login_attempts` em senha errada (campo já existe na tabela)
- ✅ Respeita `locked_until` (campo já existe — flow de bloqueio fica pra PR futura)
- ✅ Boot fail-fast se `JWT_SECRET` < 32 chars
- ✅ `requireCeoToken` agora real (era no-op) + fail-fechado se env ausente
